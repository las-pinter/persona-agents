## How It Works

This project runs **four systems** from the same sources of truth: `content/agents.json`
(theme ↔ profession ↔ persona mapping), plus the `content/personas/`, `content/professions/`, and
`content/skills/` files. Kiro and OpenCode are generated by `install.sh`; pi is an
installable extension package; Claude Code is a plugin.

### 1. Static Template Generation (Kiro)

The original system at its core is a **template-based agent generation system**.

**`content/agents.json`** is the source of truth — a registry that defines which themes
exist (`goblin`, `wh40k`, `wh40kOrk`, `pub`, `caveman`, `cyberpunk`, `catcrew`,
`fantasy`) and which professions each theme supports. Each theme+profession combination maps to a persona file, a
description, and a welcome message.

**Templates** define the platform-specific configuration for each profession:

- `platforms/kiro/templates/{profession}.json` — Kiro JSON format with tool
  permissions, allowed commands, subagent config, etc.
- `platforms/opencode/frontmatters/{profession}.yaml` — OpenCode YAML
  frontmatter with permission rules.

**Personas** (`content/personas/{theme}/*.md`) provide character voice, personality,
and speech patterns. **Professions** (`content/professions/*.md`) define role behavior
rules, delegation patterns, and failure modes. **Skills**
(`content/skills/{profession}/*/SKILL.md`) provide specialized workflow instructions.

The installer (`install.sh`) reads `content/agents.json`, and for each theme/profession
pair it:

1. Reads the platform template (Kiro JSON or OpenCode YAML)
2. Substitutes template variables (`{{THEME}}`, `{{AGENT_DESCRIPTION}}`, etc.)
3. For Kiro: writes a JSON agent file referencing external prompt files
4. For OpenCode: generates a `.md` file with YAML frontmatter + a stub comment
5. Copies resource files (personas, professions, skills) to the target directory

> **Note:** The installer never deletes files. When a profession is retired, its
> old agent files stay in `~/.kiro/agents/` and
> `~/.config/opencode/agents/`, and its profession file and templates stay in
> the installed config tree. Remove those stale files by hand. Release notes
> state the manual removal; the release text is written at release time.

### 2. Runtime Plugin Injection (OpenCode)

OpenCode agent files no longer contain inline persona content. Instead they use
a **stub comment** that the persona-agents plugin replaces at runtime.

**Stub comment format:**
`<!-- persona-agents:{theme}-{profession}:{personaFile} -->`

Example:
`<!-- persona-agents:goblin-orchestrator:bossnik-chief.md -->`

The plugin (`platforms/opencode/plugins/persona-agents.js`, self-contained plain JS — installed
as-is with no build step):

- Lives at `~/.config/opencode/plugins/persona-agents.js` after installation
- Registers the OpenCode v2 `ctx.session.hook("context", ...)` hook (the
  v2 successor of the v1 `experimental.chat.system.transform` hook)
- Before each model dispatch, scans the system prompt parts for stub markers
- When a stub is found, parses it (`parseAgentFromStubComment`) and loads the
  `profession.md + persona.md` content from disk (`loadSinglePrompt`)
- Replaces the stub fully — no marker remains

The installer copies the plugin directly — no build step:
`platforms/opencode/plugins/persona-agents.js` → `~/.config/opencode/plugins/persona-agents.js`.
It uses only Node built-ins, so it loads via auto-discovery with no
`node_modules` or package installation.

A second read-only plugin ships alongside it: `platforms/opencode/plugins/permission-auditor.js`
(installed to `~/.config/opencode/plugins/permission-auditor.js`). It appends
every permission evaluation, ask prompt, and user reply to
`~/.local/share/opencode/permission-audit.jsonl` (one JSON object per line)
without ever modifying a permission decision.
It is fully self-contained (only Node built-ins), so it needs no `@opencode/plugin` or `node_modules` in the OpenCode config directory.

### 3. Pi Extension Package

Pi is a **runtime extension package** (`platforms/pi/extension/`, TypeScript, loaded by pi
via jiti — no build step). The pi agent API consumes markdown + YAML
frontmatter, so this repo ships bare-YAML fragments in
`platforms/pi/frontmatters/{profession}.yaml` that the resolver composes
at load time with the shared `content/professions/{profession}.md` bodies, `content/personas/`,
and the `agents.json` theme ↔ profession persona mapping. The extension adds
spawn-based subagents (the `subagent` tool) with a 3-level nesting cap, a
per-agent permission gate (deny-by-default + regex allow lists), a `todo` tool
that feeds the TODOS sidebar panel, a live five-panel agent-tree sidebar, and
the `/agents`, `/persona`, `/skills`, `/sidebar`, `/agents-tree`,
`/agent-inspect`, `/runs`, and `/inspect` slash commands. Install with the pi CLI (`pi install …`, see
README.md) — `install.sh` does not generate pi files.

### 4. Claude Code Plugin

The repo root is a **Claude Code plugin** (`.claude-plugin/plugin.json`) and its
own marketplace (`.claude-plugin/marketplace.json`). The plugin copies no
content:

- **Agents** (`platforms/claude/agents/{profession}.md`) are frontmatter only:
  `name`, `description`, and tool limits. The body stays empty on purpose. A
  non-empty body would replace Claude Code's own system prompt when the agent
  runs as the main session, and it would copy the profession text.
- **Context** comes from one hook script, `platforms/claude/scripts/context.mjs`,
  run as two hooks on `SessionStart` (the main session started with
  `claude --agent persona-agents:orchestrator`) and on `SubagentStart` (an agent
  the orchestrator dispatches). The `profession` hook sends
  `content/professions/{profession}.md` verbatim. The `persona` hook sends a
  short Claude Code note plus the persona that `content/agents.json` picks for
  the `theme` option (`/config` → **Persona theme**).
- **Two hooks, not one,** because Claude Code caps each hook string at 10,000
  characters and shows only a 2,000-character preview of a longer one.
  `tests/claude-plugin.test.ts` fails if any profession, or any theme's persona
  with its note, reaches the cap.
- **Skills** load in place from `content/skills/`. `plugin.json` lists each
  skill folder; a pi-only skill is left out and named in `EXCLUDED_SKILLS` in
  the test, with the reason.
- **Doctrine** is one `PreToolUse` hook, `platforms/claude/scripts/doctrine.ts`,
  keyed on the calling agent. A plain git `add`, `commit`, `pull`, `merge`,
  `rebase`, or `tag` is allowed for the orchestrator when every part of the
  command is such a history command; a command with another part gets no hook
  decision. `git push`, every `gh pr` / `gh release` command, and the exception
  forms (for example tag force-move or delete, `git -c`, `commit --amend`,
  wrapped or runtime-shaped forms) ask for the orchestrator. All of these deny
  the rest. `cp`, `mv`, and `rsync` ask for the orchestrator and the
  implementer and deny the rest. Edits outside an agent's
  `agent-notes/` zone ask for the orchestrator and deny the planner,
  researcher, reviewer, and mascot. A hook deny wins over a user allow rule. It
  reuses the pi gate's shell parser and unwraps `cd x &&`, `sudo`/`env`/`xargs`
  prefixes, and `bash -c` payloads; an unreadable command that names a gated
  program fails closed. Sessions without a persona-agents agent are left alone.
  `tests/claude-doctrine.test.ts` holds the matrix.

## Architecture Overview

The project has **four pipelines** — one for static generation (Kiro), one
for runtime injection (OpenCode), one for runtime composition (pi), and one for
runtime context hooks (Claude Code).

### Static Generation Pipeline (Kiro)

```
agents.json  ────── reads ──┐
                             ▼
  install.sh  ── reads ──>  For each theme + profession:
                               │
                               ├── Read platform template (JSON or YAML)
                               ├── Read persona file from personas/{theme}/
                               ├── Read profession file from professions/
                               ├── Substitute template variables:
                               │     {{THEME}}               → theme name
                               │     {{AGENT_DESCRIPTION}}   → description from agents.json
                               │     {{PERSONA_FILE}}        → persona filename
                               │     {{WELCOME_MESSAGE}}     → welcome message string
                               │     {{PROFESSION}}          → profession name
                               │
                               ├── Kiro: write JSON to ~/.kiro/agents/{theme}-{profession}.json
                               ├── OpenCode: write .md (frontmatter + stub comment)
                               │            to ~/.config/opencode/agents/{theme}-{profession}.md
                               └── Copy resource files (personas, professions, skills)
                                   to target directory
```

### Runtime Plugin Pipeline (OpenCode)

```
install.sh → generates stub .md files with <!-- persona-agents:... --> comment

AT RUNTIME:
  plugin (platforms/opencode/plugins/persona-agents.js) → "context" hook → parseAgentFromStubComment()
  → loadSinglePrompt(configRoot, identity) → profession.md + persona.md
  → inject into system prompt
```

### Runtime Composition Pipeline (pi)

```
pi install → registers platforms/pi/extension/extension.ts + skills

AT LOAD TIME (extension factory / session start):
  resolver (platforms/pi/extension/resolver.ts) → platforms/pi/frontmatters/*.yaml
  → compose with content/professions/*.md + personas + agents.json mapping
  → /agents, /persona, subagent tool, todo tool, per-agent permission gate
  → shared tree log → sidebar compositor (AGENTS, SESSION, WORKSPACE, MCP, TODOS)
```

### Runtime Context Pipeline (Claude Code)

```
claude plugin install → loads .claude-plugin/plugin.json (repo root = plugin root)

AT AGENT START:
  main session (claude --agent persona-agents:orchestrator) → SessionStart
  dispatched agent (Agent tool → persona-agents:<profession>) → SubagentStart
  → context.mjs profession → content/professions/<profession>.md
  → context.mjs persona    → Claude Code note + content/personas/<theme>/<file>
                             (theme option → content/agents.json → persona file)
  → both strings arrive as additional context; the empty agent body keeps
    Claude Code's own system prompt
```

**Key design decisions:**

- **Separation of concerns:** Templates define *configuration*, personas define
  *voice*, professions define *behavior*. Each is independently editable.
- **Variable substitution:** Kiro and OpenCode templates never hardcode
  theme-specific values. All 5 placeholders are substituted at install time.
  Pi frontmatters are bare YAML and use no placeholders.
- **Three-platform output:** The same `agents.json` + templates produce agents
  for Kiro CLI and OpenCode from a single source. Pi and Claude Code expose
  the same 7 professions; every profession has a pi frontmatter and a Claude
  Code agent file.
- **On-demand loading:** The plugin loads prompts at runtime only when a stub
  comment is encountered — no pre-loading, no startup cost.
- **Self-contained plugin:** The plugin resolves resource paths relative to its
  own location (`~/.config/opencode/plugins/`), so it works without the
  original repository after installation.

## Development Setup

1. Clone the repo:

   ```bash
   git clone https://github.com/las-pinter/persona-agents.git
   cd persona-agents
   ```

2. Make sure dependencies are installed:

   ```bash
    # Check for jq (required for agent generation)
    which jq

    # Check for Node.js 22+ (required by `npm test`'s --experimental-strip-types)
    node --version

    # Install the pi extension devDependencies (typescript, typebox, pi packages)
    npm install
   ```

3. Verify the TypeScript extension and run its tests:

   ```bash
   npm run typecheck
   npm test
   ```

4. No build step — the OpenCode plugins (`plugins/*.js`) are plain Node.js
   using only built-ins and are copied as-is by `install.sh`.

5. (Optional) Preview generated output without touching your real config.
   `install.sh` writes generated agent files to `~/.kiro/` and
   `~/.config/opencode/`. `--dry-run` writes nothing:

   ```bash
   ./install.sh --dry-run --target all
   ```

6. For quick iteration, use `--theme` and `--profession` filters:

   ```bash
   ./install.sh --dry-run --target opencode --theme goblin --profession orchestrator
   ```

## Adding a New Theme

Adding a new theme means creating a whole new cast of characters (e.g., a
cyberpunk crew, a fantasy guild, a team of kitchen appliances). Each theme
needs a persona mapping for every profession. A theme has 7 professions and 7
distinct persona files, one per profession.

> **Note:** The OpenCode plugin is fully data-driven — adding a new theme
> requires **no plugin code changes**. Just add to `agents.json` and create
> persona files as described below. The stub comment format
> (`<!-- persona-agents:{theme}-{profession}:{personaFile} -->`) is parsed
> dynamically at runtime, so new themes work automatically.

### Step-by-step

1. **Add the theme to `content/agents.json`:**

   Add a new top-level key with all 7 professions. Follow the existing format:

   ```json
   {
     "mytheme": {
       "orchestrator": {
         "personaFile": "captain-example.md",
         "description": "The charismatic captain who coordinates the crew.",
         "welcomeMessage": "Alright team, what's the mission?"
       },
       "planner": { ... },
       "implementer": { ... },
       "reviewer": { ... },
       "tester": { ... },
       "researcher": { ... },
       "mascot": { ... }
     }
   }
   ```

2. **Create the persona markdown files** under `content/personas/{new-theme}/`.
   The theme needs 7 `agents.json` entries and 7 distinct persona
   files, one per profession.

   Each file should follow the [persona format](#adding-or-modifying-personas).

   ```bash
   mkdir -p content/personas/mytheme
   touch content/personas/mytheme/captain-example.md
   # ... create the other 6 distinct persona files
   ```

3. **Add the theme to the Claude Code theme picker:** append it to
   `userConfig.theme.options` in `.claude-plugin/plugin.json`.

4. **Run the installer** to verify everything generates correctly:

   ```bash
   ./install.sh --dry-run --force --theme mytheme
   ```

   If that looks good, do a real run:

   ```bash
   ./install.sh --force --theme mytheme
   ```

### What you get

The installer will generate 7 agents (one per profession) for both Kiro and
OpenCode targets, each combining the template, profession rules, and your new
persona. For OpenCode, the generated `.md` files will contain the YAML
frontmatter plus a stub comment for runtime injection. Your theme's agents are
accessible as `mytheme-orchestrator`, `mytheme-planner`, etc.

## Adding a New Profession

Professions define *what an agent does* — the role behavior rules, delegation
patterns, and tool permissions. Adding a new profession (e.g., `architect`,
`scrum-master`, `devops`) makes it available to all existing themes.

> **Note:** The OpenCode plugin is fully data-driven — adding a new profession
> requires **no plugin code changes**. You need a Kiro template, an OpenCode
> frontmatter, a pi frontmatter, a `profession.md` file, and an `agents.json`
> entry. The stub comment format
> (`<!-- persona-agents:{theme}-{profession}:{personaFile} -->`) contains the
> profession name in the agent name portion, parsed dynamically at runtime.

### Step-by-step

1. **Create the profession markdown file:**

   ```bash
   touch content/professions/{name}.md
   ```

   Follow the [profession format](#profession-files) (see Style Guide below).

2. **Create a Kiro JSON template:**

   ```bash
   touch platforms/kiro/templates/{name}.json
   ```

   Follow the existing templates for structure. Define tool permissions,
   allowed/denied commands, subagent config, and edit paths appropriate for
   the new role.

3. **Create an OpenCode YAML frontmatter:**

   ```bash
   touch platforms/opencode/frontmatters/{name}.yaml
   ```

   Map the Kiro permissions to OpenCode's permission format. See
   [Working with Templates](#working-with-templates) for details on the
   permission mapping.

4. **Create a pi YAML frontmatter:**

   ```bash
   touch platforms/pi/frontmatters/{name}.yaml
   ```

   A profession without a pi frontmatter is not exposed as a pi agent. Follow
   the existing pi frontmatters for `name`, `description`, `tools`, `skills`,
   `alwaysLoad`, and `permissions`.

5. **Create a Claude Code agent file and list it:**

   ```bash
   touch platforms/claude/agents/{name}.md
   ```

   Frontmatter only (`name`, `description`, optional `tools` or
   `disallowedTools`), with an empty body. Add its path to `agents` in
   `.claude-plugin/plugin.json`.

6. **Add the profession to every theme in `content/agents.json`:**

   Every theme in `agents.json` needs an entry for the new profession.
   Add it to all 8 themes, each with the appropriate persona file,
   description, and welcome message.

7. **(Optional) Add skills:**

   ```bash
   mkdir -p content/skills/{name}/{skill-name}
   touch content/skills/{name}/{skill-name}/SKILL.md
   ```

   See [Adding Skills](#adding-skills).

8. **Run the installer** to test:

   ```bash
   ./install.sh --dry-run --force --profession {name}
   ```

## Adding or Modifying Personas

Personas give agents their character. A persona file is a markdown document
that defines how an agent talks, thinks, and acts.

### File location

```
content/personas/{theme}/{name}.md
```

### Required format

```markdown
# {Name} the {Title} Persona

You are {Name}, the {Title}. [Brief description of who they are and their
role in the theme.]

## Personality

- [Trait 1 — descriptive, characterful]
- [Trait 2]
- [Trait 3]

## Speech Style

- [How they open conversations]
- [How they deliver information]
- [How they react to mistakes, praise, ambiguity]

## Rules

- Always stay in character as {Name}, the {Title}.
- [Behavior rule 1]
- [Behavior rule 2]
- ... (other rules)
- **Use yer own themed subagents** — dispatch `{theme}-*` agents (list a few
  by name). Dem are YOUR team members. Only use cross-theme agents if the
  user explicitly commands it.

## Notes (optional)

Additional lore or backstory.

> **Note:** Journals are handled by the orchestrator's
> `content/skills/orchestrator/journal-management/SKILL.md` skill, which builds on the
> shared `content/skills/common/journal-management-generic` skill. Do not duplicate
> journal/data-log writing protocols inside persona files.
```

### Key rules

- **First line** must be `# {Name} the {Title} Persona` (ATX header, not
  `##`).
- **Sections required:** `## Personality`, `## Speech Style`, `## Rules`.
- **Last rule** should specify the themed subagent naming convention (e.g.,
  `goblin-*`, `wh40k-*`, `wh40kOrk-*`, `pub-*`, `caveman-*`, `cyberpunk-*`,
  `catcrew-*`, `fantasy-*`).
- The `## Notes` section is optional. Journals are not written inline in
  personas — they're handled by the orchestrator's `journal-management` skill.
- Match the tone of your theme — goblins use goblin-speak, WH40K uses
  grimdark formality, Orks use Ork-speak.

## Working with Templates

Kiro and OpenCode templates are platform-specific configuration skeletons
with `{{...}}` placeholders that get filled in at install time. Pi frontmatters
are bare YAML with no placeholders.

### Kiro templates (JSON)

Kiro templates live in `platforms/kiro/templates/{profession}.json`. They use
standard JSON with the following structure:

```json
{
  "name": "{{THEME}}-orchestrator",
  "description": "{{AGENT_DESCRIPTION}}",
  "prompt": "file://~/.kiro/professions/orchestrator.md",
  "resources": [
    "file://~/.kiro/personas/{{THEME}}/{{PERSONA_FILE}}",
    "skill://~/.kiro/skills/{{PROFESSION}}/*/SKILL.md",
    "skill://~/.kiro/skills/common/project-notes/SKILL.md",
    "skill://~/.kiro/skills/common/simplified-technical-english/SKILL.md"
  ],
  "welcomeMessage": "{{WELCOME_MESSAGE}}",
  "tools": [ ... ],
  "allowedTools": [ ... ],
  "toolsSettings": { ... }
}
```

Note: each Kiro template hardcodes its own profession in the agent name and
the prompt path (for example, `"name": "{{THEME}}-orchestrator"` and
`"prompt": "file://~/.kiro/professions/orchestrator.md"`). `{{PROFESSION}}`
is still used in the `resources` array, for example
`"skill://~/.kiro/skills/{{PROFESSION}}/*/SKILL.md"`. Only the theme and other
agent metadata come from placeholders. `toolsSettings` contains the permission
mapping with `allowedCommands`, `deniedCommands`, subagent trust configuration,
and `edit` path permissions.

### Kiro ask-by-omission

Kiro has no `ask` tier. An available tool or command that is neither allowed nor
denied prompts the user. The repo doctrine holds by omission:

- A gated git write never appears in a Kiro `allowedCommands` list. `git add`,
  `git commit`, `git push`, `git pull`, `git merge`, `git rebase`, `git tag`,
  `gh pr`, and `gh release` stay unlisted, so Kiro asks.
- A destructive command stays in `deniedCommands`, so Kiro denies it. One
  case is the orchestrator tag force-move: Kiro asks by omission, while tag
  delete stays denied.

A gated git-write command in a Kiro `allowedCommands` list is a bug. This
rule is for Kiro only: the Claude Code hook, pi, and opencode allow some plain
history commands for the orchestrator. A tool that is
absent from `allowedTools` stays available, so it defaults to ask. The reviewer
and planner omit `code` for this reason.

### OpenCode frontmatter templates (YAML)

OpenCode templates live in `platforms/opencode/frontmatters/{profession}.yaml`.
They use YAML with `{{...}}` placeholders:

```yaml
description: "{{AGENT_DESCRIPTION}}"
mode: primary
permissions:
  - action: read
    resource: "*"
    effect: allow
  - action: glob
    resource: "*"
    effect: allow
  - action: grep
    resource: "*"
    effect: allow
  - action: edit
    resource: "~/agent-notes/orchestrator/*"
    effect: allow
  - action: shell
    resource: "*"
    effect: ask
  - action: shell
    resource: "git status *"
    effect: allow
  - action: subagent
    resource: "*"
    effect: deny
  - action: subagent
    resource: "{{THEME}}-*"
    effect: allow
  - action: "*"
    resource: "*"
    effect: ask
  # ...
```

Permissions are an **ordered array** of `{ action, resource, effect }` entries —
each rule pairs an action with a resource pattern and an effect (`allow`,
`ask`, or `deny`). Known action names include `read`, `glob`, `grep`, `edit`,
`shell`, `subagent`, `skill`, `execute`, `external_directory`, `question`,
`webfetch`, `websearch`, `context7`, `deepwiki`, `exa`, and `*`. (V1 action
names were renamed in the V2 schema: `bash` → `shell`, `task` → `subagent`,
`write` → `edit`, `code` → `execute`; `todowrite` was dropped.)

### Stub comment format

OpenCode agent files now use a **single-line HTML comment** instead of inline
persona content:

```
<!-- persona-agents:{theme}-{profession}:{personaFile} -->
```

The plugin replaces this at runtime with the actual `profession.md +
persona.md` content.

**Examples:**

- `<!-- persona-agents:goblin-orchestrator:bossnik-chief.md -->`
- `<!-- persona-agents:wh40kOrk-planner:sparkgutz-bigmek.md -->`

**Parsing rules** (implemented in `platforms/opencode/plugins/persona-agents.js`):

1. Extract content between `<!--` and `-->`
2. Strip `persona-agents:` prefix
3. Split on the **last** `:` — right side is `personaFile`, left side is
   agent name
4. Split agent name on the **first** `-` — right side is `profession`,
   left side is `theme`

### Permission mapping (Kiro → OpenCode)

When creating both templates for a new profession, map the permissions
roughly like this:

| Kiro concept | OpenCode equivalent |
|---|---|
| `allowedTools: ["read", "glob", ...]` | `{ action: read, resource: "*", effect: allow }`, `{ action: glob, resource: "*", effect: allow }` |
| `toolsSettings.shell.allowedCommands[]` | `{ action: shell, resource: "command*", effect: allow }` |
| `toolsSettings.shell.deniedCommands[]` | `{ action: shell, resource: "command*", effect: deny }` |
| `toolsSettings.subagent.trustedAgents[]` | `{ action: subagent, resource: "pattern", effect: allow }` |
| `toolsSettings.edit.allowedPaths[]` | `{ action: edit, resource: "path", effect: allow }` |
| `tools: ["*"]` | `{ action: "*", resource: "*", effect: ask }` |

When adding shell permissions, prefer the most specific resource pattern
possible — `"git status *"` over `"git*"`.

### Placeholder reference

| Placeholder | Where it comes from | Used in |
|---|---|---|
| `{{THEME}}` | Top-level key in `agents.json` | Agent names, resource paths, subagent patterns |
| `{{AGENT_DESCRIPTION}}` | `agents.json[theme][profession].description` | The agent's description field |
| `{{PERSONA_FILE}}` | `agents.json[theme][profession].personaFile` | Resource/prompt file references |
| `{{WELCOME_MESSAGE}}` | `agents.json[theme][profession].welcomeMessage` | Kiro welcome message |
| `{{PROFESSION}}` | Second-level key in `agents.json` | Skill paths, agent names |

## Adding Skills

Skills provide specialized workflow instructions. They're loaded by agents at
runtime to gain specific capabilities.

### File location and naming

```
content/skills/{profession}/{skill-name}/SKILL.md
```

The `SKILL.md` convention is **important** — the skill system identifies skills
by looking for files named `SKILL.md` under the profession's skill directory.

### Conventions

- **One skill per directory** — each subdirectory under `content/skills/{profession}/`
  should contain exactly one `SKILL.md` and optional supporting files (scripts,
  templates, examples).
- **Supporting files** go alongside `SKILL.md` in the same directory, or in
  a `scripts/` or `templates/` subdirectory.
- **Cross-profession skills** can live under `content/skills/common/` if they're useful
  to multiple professions (e.g., a skill that several professions load at
  startup). Pi agents guarantee such steering skills via `alwaysLoad:` in
  `platforms/pi/frontmatters/*.yaml` — the extension injects them at
  startup and warns loudly if a pattern resolves to no skill.
- **Skills are referenced by profession** — the `{{PROFESSION}}` placeholder
  resolves the path. A profession's template should include
  `skill://~/.kiro/skills/{{PROFESSION}}/*/SKILL.md` for Kiro.

### Creating a new skill

1. Create the directory:

   ```bash
   mkdir -p content/skills/{profession}/{skill-name}
   ```

2. Write `SKILL.md` with clear instructions. Include:

   - What the skill is for
   - When to load it (startup? on-demand?)
   - Step-by-step workflow instructions
   - Any scripts or supporting files it depends on

3. If the skill needs scripts, add a `scripts/` subdirectory:

   ```bash
   mkdir -p content/skills/{profession}/{skill-name}/scripts
   ```

4. Add the folder to `skills` in `.claude-plugin/plugin.json`. A skill that
   only makes sense on one other platform goes into `EXCLUDED_SKILLS` in
   `tests/claude-plugin.test.ts` instead, with the reason.

5. Test by running the installer and checking the skill file is copied:

   ```bash
   ./install.sh --dry-run --force --profession {profession}
   ```

### Commands

A command is a markdown file in `content/commands/`. The filename is the
command name, so `content/commands/retro.md` becomes `/retro` on pi, kiro, and
OpenCode. The `description` frontmatter shows in command completion. One file
serves three platforms:

- pi ships it through the `pi.prompts` key in `package.json`. Run `/reload` in
  an active session after a change.
- `install.sh` copies it to `~/.config/opencode/commands/` for OpenCode. The
  file sets no `agent` key, so the current agent runs the command.
- `install.sh` copies it to `~/.kiro/prompts/` for kiro without the
  frontmatter, because kiro documents no frontmatter for file prompts. kiro
  runs a file prompt as `/<name>`. A file with an unclosed frontmatter block
  installs unchanged, with a warning.
- A command change needs `./install.sh --force` for kiro and OpenCode, and
  `/reload` for pi.

```json
"pi": {
  "extensions": ["./platforms/pi/extension/extension.ts"],
  "skills": ["./content/skills/**/SKILL.md"],
  "prompts": ["./content/commands/*.md"]
}
```

Claude Code gets no command file. A plugin skill is a slash command there, so
the retro skill gives `/persona-agents:retro`.

A command adds no code. It loads a repo skill, and the skill holds the
procedure. `content/commands/retro.md` loads the **retro** skill
(`content/skills/common/retro/`). This split keeps command discovery in the
command file and the full procedure in the skill.

#### The retro print-only model

The retro command reviews the current session and prints the result in chat. The agent
that the user talks to runs it. It writes no durable artifact: no report file,
no skill file, no journal entry, and no permission rule. The user reads the
printed findings and actions, then decides what to do next. A finding cites
one external evidence item, so the review never rests on an agent self-grade.

The skill sets `disable-model-invocation: true`, so only the user starts it.
The pi agents list `common/retro` in `skills:`. The pi extension puts a skill
with that key in a separate "User-invoked skills" list, not in the on-demand
index, so the agent has the path for the command but does not load the skill
on a task match.
The core `SKILL.md` holds the shared method. One reference file per platform
(`references/pi.md`, `kiro.md`, `opencode.md`, `claude.md`) names the session
transcript, the permission rules, the audit log status, and the cost source.
The agent reads only the reference file of its own platform. A new platform
needs a new reference file; `tests/prompt-templates.test.ts` checks that each
one exists.

## Style Guide

### Markdown

- **Headers:** Use ATX-style (`# `, `## `, `### `), not underlined.
  The first line of any file should be a single `# Header`.
- **Line length:** Wrap at 80–100 characters for readability.
- **Code blocks:** Use fenced code blocks with language tags. Indent content
  inside lists by an extra 2 spaces when needed.
- **Tables:** Use GitHub-flavored markdown table syntax with alignment dashes.
- **Lists:** Use `-` for unordered lists, `1.` for ordered. Be consistent.
- **Links:** Use relative paths for internal files (`[CONTRIBUTING.md]`),
  full URLs for external references.
- **Emphasis:** Use `**bold**` for file paths and UI labels, `*italic*` for
  emphasis and placeholder references like `*must*`.

### Bash (install.sh and scripts)

- Follow the [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html).
- Use `set -euo pipefail` at the top of every script.
- Use `[[ ]]` over `[ ]` for conditionals.
- Quote all variable expansions: `"$file"`, not `$file`.
- Use `$(...)` over backticks for command substitution.
- Use `local` for function-scoped variables.
- Prefer `printf` over `echo` for complex output.
- Error messages go to stderr: `echo "error: ..." >&2`.
- Use `snake_case` for variable and function names.

### Persona files

```markdown
# {Name} the {Title} Persona

First paragraph: who they are, what their deal is.

## Personality

- Bullet list of personality traits, in-character

## Speech Style

- Bullet list of speech patterns and conventions

## Rules

- Behavior rules
- Last rule: **Use yer own themed subagents** — dispatch `{theme}-*` agents
```

Required sections: `## Personality`, `## Speech Style`, `## Rules`.
Optional section: `## Notes` (lore/backstory only — no journal protocols).

### Profession files

```markdown
# {Profession}

First paragraph: role summary.

## Startup

- Optional. Skills and first steps to load before any user input. When present,
  this section comes first — before Core Behavior.

## Core Behavior

- Behavior rules for this profession
- The FIRST rule MUST establish that profession rules take precedence over
  persona instructions on matters of function.

## <Role Sections>

- Optional role-specific sections (for example `## Implementation Approach`
  or `## Review Types`) usually sit between Core Behavior and When to Defer.

## When to Defer

- Situations where this profession should escalate rather than act

## Failure Modes (never do these)

- List of things the agent must never do

## Output Format

- Description of how results should be presented

## Skills

- References to skill documents
```

Required sections: `## Core Behavior` (with precedence rule),
`## When to Defer`, `## Failure Modes`, `## Output Format`, `## Skills`.

The required relative order is: `## Startup` (optional, first) →
`## Core Behavior` → `## When to Defer` → `## Failure Modes` →
`## Output Format` → `## Skills`. Every section in a profession file must be
one of these or an allowed role or trailing section. Role sections usually sit
between `## Core Behavior` and `## When to Defer`, but may instead sit after
`## When to Defer` (the orchestrator places `## TODO Lists`,
`## Journal Management`, `## Project Notes`, and `## Context Discipline
(CRITICAL)` there). Trailing sections may sit before or after `## Skills`; the
researcher's `## Research Documentation` sits between `## Output Format` and
`## Skills`. `## Startup`, when present, comes first and lists the skills
loaded before any user input; a pi agent's `alwaysLoad` frontmatter must match
that list (doc-lint condition 5).

> **Note:** `content/professions/implementer.md` is the only implementer profession.
> Language-specific guidance lives in the implementer skills and in
> `common/skill-resolution`, not in a separate profession.

> **Note:** Mascot/novelty professions that don't perform tool-based work
> (e.g., `content/professions/mascot.md`) may omit most or all of these sections.
> All other professions should include all required sections.

### JSON/YAML templates

- **JSON:** Use 2-space indentation. Double quotes for all strings. No
  trailing commas. Valid JSON only (checked by `jq`).
- **YAML:** Use 2-space indentation. No tabs. Use the `.yaml` extension.
  Strings don't need quotes unless they contain special characters.

This is a personality project. Don't make the contributing guide the driest
thing in the repo. Use examples. Be a little playful. The personas should
make people smile — the code should make them productive.

release:
